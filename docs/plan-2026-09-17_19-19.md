# Plan — MLP scorer (2026-09-17_19-19)

Status: proposed.

## Need

The linear scorer ties `aggressive` (+0.003, CI [−0.020, 0.026]) and cannot move past it on a
budget large enough to rule out sampling noise — see [train-log.md](./train-log.md). Thirty
weights can only express “add up weighted feature values”, which for this game reduces to
“prefer a fat pile, prefer Zombie”. Anything conditional is out of reach.

The point of an MLP here is precisely conditionality. Plays like *hold the shotgun until the
zombie share is high*, or *dump a small pile when my hand is nearly empty*, need a feature to
change meaning depending on another feature. A dot product cannot do that; one hidden layer can.

## Three things the linear path gets away with and an MLP will not

**Unnormalized features.** `encodeViewVector` emits `livingCount` up to 64 and `pileSum` above
40, next to booleans. A linear model absorbs that in the weight scale. Feed it to `tanh` and
every unit saturates immediately. So the MLP path needs fixed per-feature scales.

The scales are constants, not learned statistics, and they apply **only** on the MLP path.
`concatFeatures` stays untouched, because `docs/weights-latest.json` holds `linear-v1` weights
that were fitted against the raw features and must keep reproducing.

**Zero initialisation.** Stage B starts from zeros, which for a linear model is exactly the
uniform policy. For an MLP zeros are a dead point: hidden activations are `tanh(0) = 0`, so
perturbing the output layer changes nothing, and any signal needs both layers perturbed
favourably in the same step. The MLP starts from a small seeded random draw instead.

**Step size.** A perturbation of every coordinate with `sigma` moves the parameter vector by
about `sigma · sqrt(dim)`. Going from 30 to 257 parameters at a fixed `sigma = 0.2` triples the
step length. Rather than guess, sweep `sigma` on a short budget before committing to a long run.

## Shape

Input 30 → hidden 8 (`tanh`) → 1 score. That is `30·8 + 8 + 8 + 1 = 257` parameters.

Eight units, not sixty-four: the search is a (1+λ) hill climber with 24 candidates per
generation, and its cost per useful step grows with dimension. Widen only if 8 beats linear and
still looks limited.

Everything downstream is unchanged — softmax over legal actions, sample with `ctx.random`.

## Weight files

`kind: 'mlp-v1'` alongside `linear-v1`, with `hidden` recorded so a file describes its own
architecture. `npm run simulate --weights` dispatches on `kind`, so old files keep working.

`trainEs` currently hardcodes `zeroWeights` and `scoredPolicy`. It takes a small `Model`
(`dim`, `init`, `policy`) instead. This generalisation is driven by an actual second case, not
by anticipation.

## Runs

The MLP does roughly ten times the arithmetic per action, and the linear run already took 47
minutes, so the same budget could take hours. Therefore:

1. Sigma sweep, short budget (15 × 16 × 30), for `sigma` in 0.05 / 0.1 / 0.2. Scratch paths.
2. One long run at the best sigma, budget chosen from the measured seconds per generation.
3. Held-out at 200 episodes against `randomLegal` and `aggressive`, same as the linear run.

## Success

Beating `aggressive` head-to-head with a confidence interval clear of zero. Anything else —
including another tie — is recorded as a result about capacity, and the next question becomes
whether the observation is rich enough rather than whether the model is.

## Review against the core principles

**KISS.** One hidden layer, eight units, `tanh`, constant feature scales. No optimiser change,
no schedule, no new metrics.

**YAGNI.** No second hidden layer, no PPO, no learned normalisation, no `/watch` wiring.

**SRP.** `mlp.ts` owns the architecture, `scorer.ts` stays linear, `train.ts` loses its
hardcoded model, `features.ts` gains only the scale constants.

**DRY.** Both models share the feature encoders, the softmax sampler and the differential
harness.
